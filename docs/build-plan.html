StoryFrames Backend: Step-by-Step Connection Plan

Frontend (Vite + React) ↔ Socket.IO ↔ FastAPI ↔ PostgreSQL. You write the code and the schema. This document says what to do, in what order, and how to know a step is finished.

How to use this plan

  • Work in order. Do not start a step until the previous "Done when" check passes.
  • Every step ends with a Done when check. If it fails, fix it before moving on.
  • Keep the frontend running while you work. Each socket step ends with a real test in the browser.

Part 1: Environment and configuration

Goal: the backend and database start reliably on your machine, with one source of truth for the database URL.

Step 1.1: Decide where each piece runs

  • Recommended for development: PostgreSQL in Docker, backend in a local virtual environment (venv). Reloads are faster and debugging is easier.
  • Keep the backend service in docker-compose.yml for later, when you deploy.
Done when
You can say, in one sentence each, where the backend, the database, and the frontend run.

Step 1.2: Clean up the environment files

  • Confirm .env is in .gitignore, so secrets are never committed.
  • Keep .env.example as the template: every variable name with a placeholder value, no real secret.
  • Make sure every variable the code reads appears in .env.example.
Done when
git status shows .env as ignored, and a new developer could copy .env.example and fill it in.

Step 1.3: Give the database URL two correct forms

  • From your Windows machine (backend in venv): host localhost, port 5432.
  • From inside Docker (backend container): host db (the compose service name), port 5432. Inside a container, localhost means the container itself, so it fails.
  • Use the driver that matches the installed package. psycopg2-binary is in requirements.txt, so the scheme is postgresql+psycopg2://.
  • Write both forms in .env.example as comments so they are not mixed up.
Done when
You can state which URL to use in each place, and it matches the driver in requirements.txt.

Step 1.4: Pass the database URL into the backend container

  • The backend service in docker-compose.yml has no environment variables. Give it the container form of the URL, using an environment entry or an env_file entry.
  • Keep the password in one place and reference it, rather than writing it twice.
  • POSTGRES_PASSWORD on the db service must match the password in the URL.
Done when
docker compose config shows the DATABASE_URL value on the backend service.

Step 1.5: Make the settings loader independent of the working folder

  • app/db/database.py reads .env relative to the current folder, so starting from another folder can fail.
  • Point the settings loader at the backend root, not the current directory.
  • Move the settings class to the current pydantic-settings style (model_config) to remove the deprecation warning from class Config.
  • Make a missing DATABASE_URL produce a readable error, not a stack trace from deep inside SQLAlchemy.
Done when
Starting from the backend root and from one folder up gives the same settings, and a missing DATABASE_URL gives a clear message.

Step 1.6: Make Python and the dependencies match Docker

  • The Dockerfile uses Python 3.12. Create the venv with Python 3.12 so local and container behavior match.
  • requirements.txt looks like it is saved as UTF-16. Re-save it as UTF-8 (Notepad: Save as, encoding UTF-8).
  • Create a fresh venv, install from requirements.txt, and confirm there are no errors.
  • Keep the venv folder out of git (check .gitignore).
Done when
A brand-new venv installs cleanly, python --version shows 3.12.x, and pip freeze matches the pins.

Step 1.7: Start the database and check it from the host

  • Run docker compose up -d db.
  • If a local PostgreSQL already uses port 5432, stop it or change the host port in compose. The container port stays 5432.
  • Check health with docker compose ps. If it is not running, read docker compose logs db.
Done when
db shows as running, and you can connect to it from the host using the Step 1.3 URL.

Part 2: Backend boots and answers over HTTP and Socket.IO

Goal: the server starts, answers a health check, and accepts a Socket.IO handshake.

Step 2.1: Start the server with the correct target

  • Run uvicorn from the backend root with the target app.main:app. Keep that name: it refers to the combined Socket.IO and FastAPI app.
  • Use --host 0.0.0.0 so phones on your Wi-Fi can reach the server later (Step 4.5).
  • Keep --reload while developing.
Done when
The server reports it is listening on port 8000 with no errors.

Step 2.2: Verify the HTTP health route

  • Open /health in a browser.
  • Include the router from app/router/players.py in the app. It is defined but never included, so its routes are unreachable.
Done when
/health returns ok, and the players route appears in the API docs at /docs.

Step 2.3: Verify the Socket.IO endpoint over plain HTTP

  • The handshake lives at /socket.io/. Request it in a browser with the protocol and transport parameters for polling (EIO=4 and transport=polling).
  • A correct response starts with a digit and includes a session id. "Not found" means the mount is wrong.
Done when
The handshake URL returns a Socket.IO open packet containing a session id.

Step 2.4: Replace print statements with logging

  • The connect and disconnect handlers use print. Switch to the standard logging module so output can be filtered by level later.
  • Log the session id, the disconnect reason, and the auth key names. Never log auth values.
Done when
Connect and disconnect messages appear through the logger at INFO level.

Part 3: Database connection and migrations

Goal: the app reads and writes PostgreSQL, and Alembic manages the schema.

Step 3.1: Add a database health route

  • Add a route such as /health/db that runs a trivial query through the session from get_db.
  • When the database is down, return a clear failure status and message, not an unhandled 500.
Done when
/health/db returns OK while the container runs, and a clear failure after docker compose stop db.

Step 3.2: Decide sync or async database access (before writing models)

  • The engine is synchronous (create_engine), but Socket.IO handlers are async.
  • Recommendation: keep the synchronous engine for now. Run database work from async handlers through a threadpool helper, and keep each call short. Switch to async SQLAlchemy only if you measure a problem.
  • Write the decision in one line in your notes so it is not reopened later.
Done when
The decision is written down, and you know which helper socket handlers will call for database work.

Step 3.3: Connect Alembic to your settings and metadata

  • In alembic/env.py, set the target metadata to your declarative base's metadata. It is None now, so autogenerate sees no tables.
  • Read the database URL from your settings, not from a second copy in alembic.ini. One source of truth.
  • Import every model module before autogenerate runs, or its tables are silently skipped.
Done when
alembic current runs without errors on the empty database.

Step 3.4: Create and apply the first migration

  • Create a first revision for one small table only. The full schema comes in Part 5.
  • Apply it with alembic upgrade head, then confirm the table in a SQL client (DBeaver, pgAdmin, or docker compose exec db psql).
  • Practice one downgrade and upgrade so you know rollback works before you need it.
Done when
The table exists, alembic downgrade -1 removes it, and alembic upgrade head recreates it.

Part 4: Frontend connects to backend (first socket handshake)

Goal: the browser opens a Socket.IO connection to the backend, and both sides show it.

Step 4.1: Move the backend address into a frontend env variable

  • src/utils/socket.ts hardcodes http://localhost:8000. Move it to an environment variable.
  • Vite exposes only variables starting with VITE_. The current BACKEND_APP_URL in the frontend .env is invisible to the browser, so rename it to VITE_BACKEND_URL.
  • Add a frontend .env.example with the same key and a placeholder.
  • Restart the Vite dev server after any .env change. Vite reads it only at startup.
Done when
Changing VITE_BACKEND_URL and restarting Vite changes the address the socket uses.

Step 4.2: Decide the allowed origins

  • The Socket.IO server allows every origin (*). That is fine for the first test. Write down the list you will use: http://localhost:5173, and your PC's LAN address on port 5173 for phone testing.
  • Restrict the list before deploying (Part 8).
Done when
The exact origin list is written down, using your PC's current LAN IP.

Step 4.3: Turn the connection back on in the app

  • App.tsx has the socket disconnected. Re-enable the connect call and the connect, disconnect, and connect-error listeners.
  • Make the unmount cleanup call disconnect, so React's development double-mount does not leave two sockets open.
Done when
The browser console shows "Connected" with a socket id, and the backend logs a connect line for the same id.

Step 4.4: Add a ping event as the first end-to-end test

  • Backend: one handler, client.ping, that replies with server.pong and the server time. Use a Socket.IO acknowledgement so the client receives the reply directly.
  • Frontend: send one ping after connecting and log the round-trip time (a temporary log is fine).
Done when
The console prints a round-trip time and the backend logs the ping. Two-way traffic is proven.

Step 4.5: Test from a phone on the same Wi-Fi

  • Run the backend with --host 0.0.0.0 (Step 2.1), and the Vite server with --host so it listens on the LAN.
  • Allow ports 8000 and 5173 through Windows Firewall for private networks.
  • Set VITE_BACKEND_URL to the LAN address. On a phone, localhost means the phone itself.
  • Add the LAN origin from Step 4.2.
Done when
The phone loads the game page and the ping round-trip works.

Step 4.6: Test reconnect behavior

  • Stop the backend while the page is open. The frontend should show a disconnected state and retry on its own.
  • Start the backend again. The socket should reconnect with a new socket id.
Done when
The frontend reconnects after a backend restart, without a page reload.

Goal: decide the data model before writing more events. You design it. This section lists what you must decide so nothing is missed.

Step 5.2: Decide identity and ids

  • Decide how a guest is identified across reconnects. The frontend keeps one id per browser tab in sessionStorage. Decide whether the server issues the id on connect, or the client sends its own.
  • Decide id types: UUIDs everywhere, or integer keys internally with UUIDs for anything sent to clients.
  • Decide how room codes are generated and kept unique, and when old rooms expire.
Done when
A written rule says where each id comes from and who may use it.

Step 5.3: Decide the source of truth for live game state

  • Decide which state lives in memory (phase, timers, connected players) and which goes to PostgreSQL (rooms, rounds, scores, history).
  • Decide whether writes happen immediately or in the background. The design documents prefer background writes, so gameplay never waits on the database.
  • Decide what is lost if the server restarts mid-round. A simple rule for development is acceptable.
Done when
You can answer: "If the server restarts mid-round, what is lost and what is kept?"

Step 5.4: Decide how stroke data is stored

  • Option A: one row per stroke, with points stored as JSON. Simple, and matches the frontend's current format.
  • Option B: one row per drawing event (stroke, undo, clear) in an ordered event table. Easiest to replay and debug.
  • Decide how long the event log is kept, and whether it is kept after a round ends.
Done when
You have chosen A, B, or a combination, and can justify it in two sentences.

Step 5.5: Write the schema diagram

  • Draw the tables and their relationships. Mark primary keys, foreign keys, and unique constraints.
  • Check each query you expect: "get a room with its players", "get the current round's scene cards", "list a room's drawing events in order". The schema must answer each one.
Done when
Every expected query can be answered from the diagram without guessing.

Step 5.6: Decide the team and match model

  • Separate team (Team A and Team B, fixed for the whole match) from role (artist or guesser, changes every round). The current frontend stores only a role per player, so this is a schema change.
  • Decide the round count. The design documents use 6 rounds by default, so each team draws three times. The create-room form has no round count yet.
  • Decide the rule for uneven teams and for the minimum scene count (the documents raise 2 artists as a case to handle).
Done when
For a 5-player room, you can state who is on each team and who draws in rounds 1 and 2.

Part 6: Socket events, one at a time

Goal: build the game flow over Socket.IO in small steps. An event is finished only when the frontend can trigger it and see the result.

Rules for every event: (1) write its payload in the protocol doc first; (2) validate every field on the server and reject bad input with an error reply; (3) use an acknowledgement for requests that need an answer; (4) broadcast state changes to the room; (5) test from the browser before starting the next event.

Protocol document (do this first)

Create docs/websocket-protocol.md in the backend. For each event, list: name, direction (client to server, or server to clients), payload fields with types, the acknowledgement reply, and the error codes it can return. Use the envelope the frontend already sends for drawing events: version, eventId, roomCode, playerId, sequence, sentAt, plus the type-specific fields.

Checks to add to each event

  • Authorization: the sender is in the room and has the right role (host, artist).
  • Phase: the event is allowed in the current phase (for example, no strokes outside the drawing phase).
  • Order: sequence increases per player; duplicates are dropped by eventId.
  • Size: reject strokes with too many points or too large a payload.

Part 8: AI story and scene generation

Goal: before each round, the server asks an AI for a story and one scene card per artist, validates the result, and stores it. The AI never sees players, scores, or drawings, and it never runs while people are drawing.

Step 8.1: Define the AI output contract

  • Each round needs one structured response: the story (3 to 8 sentences, self-contained, funny, family-safe), one scene card per artist, and for each scene a short list of key story beats.
  • The key beats are what scoring (Part 9) matches guesses against. Ask for them now, so scoring never has to guess what the story was about.
  • Parse the response into a fixed structure. Reject any response that does not match it, and never pass raw model text to clients.
Done when
You have a written example response for 3 artists, and the server rejects a malformed one.

Step 8.2: Choose a provider and keep it swappable

  • Put the provider behind one interface, for example generate_round(category, difficulty, artist_count). Build one concrete provider first. The design documents require the rest of the code to not depend on which one it is.
  • Keys live only in the backend's .env (provider name, API key, model name). Add the names to .env.example. Never send them to the frontend.
  • A small, fast model is usually enough for story and scene generation. Upgrade only if output quality is poor.
Done when
A one-off test calls the provider with a fixed category and gets back a parsed response.

Step 8.3: Set the scene count rules

  • The number of scenes equals the number of artists. Decide a minimum (the phase plan suggests about 3, so a 2-artist round asks for a longer story) and a maximum (about 8, by splitting large teams into parallel sub-stories).
  • Write the rule in your notes, and make the limits constants rather than numbers scattered through the code.
Done when
The rule is written, and a test shows it works for 2, 3, and 8 artists.

Step 8.4: Write the scene validator (in code, not in the prompt)

  • Do not trust the model to follow the scene rules. Check them in code:
    • The scene is a visual instruction (for example, it starts with "Draw" or describes a subject doing something).
    • No causal or sequencing words such as because, before, after, then, however, accidentally, suddenly, later.
    • Not a single word or abstract connector: enforce a minimum word count.
    • No full spoilers: a scene must not repeat the story's final beat.
    • Balance: flag a round where one scene carries far more story detail (beat count or word count) than the others.
  • If a check fails, regenerate. Set a retry limit (2 or 3 attempts).
Done when
The validator rejects the bad examples from the design document and accepts the good ones.

Step 8.5: Generate before drawing, not during it

  • When the host starts the game, move to a GENERATING state and broadcast the room state without any story content.
  • Generate in the background so the socket loop keeps responding. Then move to DISTRIBUTING (send each artist their private scene.assigned) and then DRAWING, with the server-set deadline.
  • Decide whether to pre-generate the next round during the current round's guessing and scoring. That removes the wait between rounds. Document the decision.
Done when
Starting a game shows "Generating story" to everyone, and the drawing timer starts only after the content is ready.

Step 8.6: Plan for AI failures

  • On a timeout or error, retry with a short backoff (2 attempts).
  • If it still fails, use a fallback round from a local file of prewritten stories, in the same structure. The game must keep moving.
  • Flag fallback rounds in the room state so the host knows, and log every fallback.
Done when
With a wrong API key or no network, a game still reaches DRAWING using fallback content.

Step 8.7: Store the round content

  • Save the story, the scene cards, the key beats, the provider, the model name, the prompt version, the time, and whether it was a fallback. You need this for replay and debugging.
  • The story stays secret until the reveal (Part 9). Store it, but never send it before then.
Done when
A finished round's story and scenes can be read back from the database.

Step 8.8: Update the frontend

  • Show a "Generating story" state between the lobby and the drawing screen.
  • Take scene cards from scene.assigned, not the placeholder list in src/constants/game.ts. Remove that list once nothing uses it.
Done when
Each round shows AI-generated scene cards, and they differ between rounds.

Part 9: Guessing, reveal and scoring

Goal: after drawing, guessers write their reconstruction, the story is revealed, and both teams are scored by the server.

Step 9.1: Decide the scoring rules first

The two design documents disagree. Version 0.1 scores semantic similarity, speed, scene clarity, and a balance bonus. Version 0.2 scores artists by community votes. The phase plan says the first version uses keyword matching only. Pick one set before you write any scoring code.

Recommended first version:

Done when
You have written the final weights and chosen whether artists are scored by the opposing guess (recommended) or by votes.

Step 9.2: Accept guesses

  • Add the guess.submit event (text only). Only guessers may send it, and only during the GUESSING phase.
  • Validate the text: not empty, a length limit, and rejected once the deadline passes.
  • Decide whether each guesser submits their own guess and the team score uses the best one, or whether each team submits one guess (for example, the latest before the deadline). Write the rule down.
Done when
A valid guess is stored, empty and late guesses are rejected, and a duplicate is handled by your rule.

Step 9.3: End guessing and reveal the round

  • End the phase when the timer runs out or every guesser has submitted. Move to REVEAL and broadcast the story, the scene cards, the scene order, and all drawings.
  • Decide who may see what in each phase. Use this as the rule your server enforces:

Done when
All clients get the reveal at the same moment, and an inspection of socket traffic shows the story was never sent earlier.

Step 9.4: Score guesses on the server

  • Normalize text (lowercase, remove punctuation, match simple word forms). Count how many of the story's key beats appear in the guess, then convert to a 0 to 100 score.
  • Store each guess's score and which beats matched. The reveal screen can then show why a guess scored what it did.
  • Keep this as a pure function that takes text and beats, so you can test it.
Done when
A unit test with a fixed story and guess returns the expected score and matched beats.

Step 9.5: Score the drawings and the rest of the round

  • Compute artist points from the opposing guess score (Step 9.1), plus any speed or self-reconstruction bonuses you chose.
  • Compute all points in one pure function that returns a per-player and per-team breakdown.
Done when
Unit tests with fixed inputs produce the expected breakdown for both teams.

Step 9.6: Add community votes (optional, after the first version works)

  • After the reveal, each player votes once for the most helpful drawing, and never for their own.
  • The server counts votes and adds a bonus to each artist per vote. Fun awards do not affect points.
Done when
One vote per player is enforced, self-votes are rejected, and vote points appear in the round score.

Step 9.7: Broadcast results and update the frontend

  • Send round.reveal with the reveal content, then round.scored with the breakdown.
  • Frontend: a reveal screen showing the comic strip in story order (drawing plus sentence), the guesses with matched beats, and the round score per team.
Done when
Every client sees the same reveal and the same score breakdown.

Part 10: Round switching and match end

Goal: after scoring, roles swap, the next round starts, and the match ends with a winner.

Step 10.1: Write the round state machine

  • Full loop: LOBBY, GENERATING, DISTRIBUTING, DRAWING, GUESSING, REVEAL, SCORING, RESULTS, then either the next round's GENERATING or FINISHED.
  • Write the allowed transitions as a table in the protocol doc. Any other transition is rejected.
Done when
A unit test tries an illegal move (for example, DRAWING straight to SCORING) and it is rejected.

Step 10.2: Swap roles between rounds

  • Each round, one team draws and the other guesses. Next round they switch. Compute roles from the team and the round number, rather than storing them separately, to avoid drift.
  • Decide the rule for uneven teams, for example rotating one player per round so everyone draws at least once.
Done when
A written 4-player table shows who draws in each round, and each player draws equally often.

Step 10.3: Set the round count and match length

  • Default is 6 rounds, so each team draws 3 times. The count must be even so both teams draw equally. Enforce this on the server.
  • Add the round count to the create-room settings and the frontend form.
  • Optional: escalate difficulty across rounds (Easy, then Medium, then Hard), as the design document suggests.
Done when
A 6-round match runs from start to finish, and the round counter shows on every screen.

Step 10.4: Decide the winner and tie-breaks

  • At FINISHED, the winner is the team with the higher cumulative score. Show the full leaderboard.
  • Tie-break options from the design document: a sudden-death round (one short scene each), then total scene clarity bonus, then co-winners in casual mode.
  • Recommended: co-winners first (simplest), and add sudden death later.
Done when
The final screen shows both teams with a winner or co-winners, and a forced tie triggers your chosen rule.

Step 10.5: Allow a second match in the same room

  • When the host chooses "play again", start a new match with the same players and zero scores. Keep the first match's history in the database.
  • This builds on the game.reset event from Part 6.
Done when
The second match starts at zero, and the first match is still in the database.

Step 10.6: Update the frontend for teams and roles

  • The lobby shows Team A and Team B, not only artists and guessers. Each round, show the player's role (Artist or Guesser) and the round counter.
  • Add a team scoreboard and a final leaderboard screen.
Done when
A full match plays in four browsers, and every screen shows the correct team and role for the current round.
